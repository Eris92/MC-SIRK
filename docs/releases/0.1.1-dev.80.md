# SIRK Management Platform 0.1.1-dev.80

Date: 2026-08-13
Status: development pre-1.0, real MeshCentral/Jira acceptance pending

## Scope

Real `0.1.1-dev.79` smoke confirmed the `assignmentAttribute()` word-list widening was not sufficient by itself: `Sprzęt do protokołu` still returned only `Komputer`. The user also reported the protocol PDF is "wrong" (a plain-text document, not the styled A4 layout).

## Investigation

A permissive-matching change (matching a Jira user's identity against any displayed attribute value, regardless of attribute name) was tried and reverted after it broke an existing regression: unrelated plain text (e.g. a `Notes` field that happens to contain a Jira account ID substring) started incorrectly binding equipment to a user. That was precisely the false-positive class `0.1.1-dev.66` was written to prevent, so this build does not carry that change.

Real dev.63 (2026-08-11) is confirmed by the user to be the last version where `Sprzęt do protokołu` returned every equipment type. At that revision, `entryMatchesUser()` matched a user's identity against any attribute text with no name/structure gating at all, and the canonical AQL was already scoped to `objectType in objectTypeAndChildren("Sprzęt użytkownika")` (unchanged since). Determining the exact, safe matching rule that reproduces dev.63's equipment coverage without dev.66's false-positive regression requires the real tenant's raw Jira Assets response shape for a non-`Komputer` object (e.g. `Monitor`) — this has been requested from the user and is still outstanding.

## Changes

- Revert the reverted-in-testing permissive-matching attempt; `entryMatchesUser()`/`assignmentAttribute()` remain exactly as shipped in `0.1.1-dev.79`.
- Stop silently discarding the browser-renderer failure reason when `html-pdf-renderer.js` falls back to the dependency-free plain-text PDF. `directFallback()` now stamps `pdf.sirkFallbackReason` with the bounded browser failure detail, and `jira-protocol-service.js` appends it to the returned `message` so the actual Edge/Chrome failure is visible in Results instead of only producing a plain-text document with no diagnostic.
- Add a regression asserting the fallback reason surfaces in the protocol result message.

## Acceptance gate

Two real MeshCentral/Jira smoke items remain open:

1. `Sprzęt do protokołu` returning every equipment type assigned to the selected user, not only `Komputer` — blocked on the raw Jira Assets attribute payload for a non-`Komputer` object from the real tenant.
2. The protocol PDF rendering as the full styled A4 document — the new fallback-reason message (visible after running the protocol) should show the actual Edge/Chrome failure so it can be diagnosed instead of guessed at.
