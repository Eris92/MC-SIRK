# SIRK Management Platform 0.1.1-dev.72

Date: 2026-08-12  
Status: development build, no product release

## Summary

Real `0.1.1-dev.71` smoke showed that `Jira cache - assets` could remain on `Executing script...` for an operationally unacceptable time and block protocol asset resolution behind the same in-flight workspace refresh.

The v3 cache format reduced the persisted snapshot, but refresh still accumulated every raw, deeply nested Jira AQL object in memory until the last page completed and fetched pages sequentially. This preserved high peak memory pressure and long wall-clock time during a forced rebuild.

`0.1.1-dev.72` keeps the existing single Jira Assets cache owner and changes the refresh lifecycle:

- each AQL page is normalized and compacted before it is retained in the refresh accumulator;
- when Jira returns a stable total and full 500-item pages, remaining pages are fetched with bounded concurrency of three;
- fallback object-type attribute discovery uses the same bounded concurrency;
- page scheduling has a 180-second safety bound and each Jira request retains its existing 30-second timeout;
- a non-forced protocol lookup can reuse an existing v3 snapshot while an explicit refresh is already in flight instead of joining that refresh unnecessarily;
- unknown Jira pagination shapes retain the previous bounded sequential fallback.

No new polling loop, cache owner, client-side AQL authority or credential path is introduced.

## Verification

- regression for a 2000-object workspace verifies exactly four required AQL pages, concurrent execution bounded to three, complete result retention and compact v3 persistence;
- full `npm test` and Windows interactive-shell smoke are required on the exact candidate head before merge.
