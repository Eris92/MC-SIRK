# SIRK Management Platform 0.1.1-dev.67

## Jira protocol PDF generation fallback

Real `0.1.1-dev.66` smoke proved that both Microsoft Edge CLI headless print paths still fail under the MeshCentral Windows service context and return no usable `protocol.pdf`.

`0.1.1-dev.67` keeps the styled HTML browser renderer as the preferred path, but `server/core/jira-protocol-service.js` now reuses the existing dependency-free `pdf-text-renderer.js` exactly once when the browser renderer fails or returns invalid PDF bytes. The protected artifact is still created only after `%PDF-1.` validation. If both renderers fail, the final bounded error retains both causes.

No `--no-sandbox`, external PDF dependency, persistent browser profile, polling loop or second protocol lifecycle owner was added. The user-supplied Jira PowerShell workflow bodies were reviewed; the canonical seed retains the current workspace-wide Jira metadata so the prior assigned-Assets scope regression is not reintroduced.
