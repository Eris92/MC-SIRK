## Approval Center confirmation UX and direct message defaults

Real MeshCentral smoke on dev.120 showed three workflow gaps: built-in SMS/mail scripts still defaulted to Level 1 approval, requester-confirmed Jira requests stayed in the actionable view while CMDB finalization was running, and the confirmation UI exposed only the generic Jira Asset Protocol description.

Changes:

- make built-in `Send SMS`, `Send Voice SMS` and `Send mail through SMTP Relay` default to no pre-approval;
- keep the direct-execution exception scoped to the existing stable `SmsSend`, `VmsSend` and `RelayMailSend` workflow identities, so ordinary My Scripts with an empty approval list still retain the configured Level 1 fallback when `allowNoApproval` is disabled;
- continue honoring explicitly configured Level 1/2/3 approval on those message workflows;
- after native requester confirmation is accepted, reuse the existing `confirming` state immediately in Approval Center and remove that request from the local actionable view before waiting for Jira finalization;
- keep the backend approval service as the authoritative confirmation/finalization owner; success and failure still resolve to the persisted `completed` / `failed` state with existing replay and concurrency guards;
- show authoritative prepared Jira protocol context as `User:` and changed `Assets:` in actionable cards, table summaries and the native confirmation dialog;
- derive that context only from the already prepared public `result.data`; no extra Jira request, timer, polling loop, observer or second lifecycle owner is added;
- preserve requester/SiteAdmin authorization, Cancel -> Rejected behavior, protected PDF and Jira CMDB exactly-once semantics.

Verification:

- `test/approval-message-ux.test.js` covers direct message defaults, the ordinary-script fallback boundary, immediate `confirming` transition ordering and Jira User/Assets context reuse;
- existing SMSAPI, SMTP Relay, requester confirmation/cancellation and Jira confirmation regressions remain required;
- full `npm test` and Windows interactive-shell smoke are required on the exact versioned PR head before merge.

No tag or GitHub Release is created for this development revision.
