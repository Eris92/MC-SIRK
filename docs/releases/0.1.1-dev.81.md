# SIRK Management Platform 0.1.1-dev.81

Date: 2026-08-13
Status: development pre-1.0, real MeshCentral/Jira acceptance pending

## Scope

The user supplied the real tenant's `jira-assets-cache.json` (produced by `Jira Cache Assets`). It showed the actual root cause of `Sprzęt do protokołu` returning only `Komputer`: the cached snapshot contained exactly 1000 raw objects (540 `Komputer`, 283 `Czytnik kodów`, 130 `Drukarka`, 31 `Pendrive szyfrowany`, 13 `Tablet`, 2 `Akcesoria`, and only **1** `Monitor`), even though the tenant's schema tree shows 181 `Monitor` objects alone. Every other equipment type was almost entirely absent from the cache before any user-matching logic ever ran.

The one `Monitor` object that *was* cached had a correctly populated `Osoba_odpowiedzialna` `matchValues` array (including the assigned person's lowercased display name and object aliases), confirming the `0.1.1-dev.79` assignment-attribute fix works correctly. The real bug was earlier in the pipeline: pagination.

## Root cause

`server/core/jira-asset-service.js`'s bounded-concurrency Assets fetch (`fetchConcurrent`) computes how many pages to request from the first page's reported `totalFilterCount`/`total`, then stops once it has fetched that many pages — without ever checking whether the last page it actually received still reported `hasMoreResults: true`. Jira's Assets AQL endpoint can (and, for this tenant, does) report a `totalFilterCount` capped at 1000 regardless of the real result count, while `hasMoreResults` on the page at that boundary still correctly says there is more data. The code trusted the capped total, silently dropping every object beyond it — which for this tenant's AQL ordering meant almost all non-`Komputer` equipment.

## Changes

- `fetchConcurrent()` now returns the last page it actually fetched (by highest `startAt`) instead of discarding page metadata.
- After the concurrency-bounded batch driven by the reported total completes, the fetch loop checks that last page's own `more`/`hasMoreResults` signal and keeps paging sequentially past the (possibly capped) total until the real end of results or the existing `MAX_ASSET_SCAN_PAGES` safety bound is reached.
- Add `test/jira-assets-capped-total-pagination.test.js`, reproducing a Jira response that reports `totalFilterCount: 1000` while the real result set is 1200 objects and `hasMoreResults` stays `true` past the cap; asserts the full 1200-object result is fetched and not marked truncated.
- No change to AQL scope, cache schema v4, concurrency bound, or assignment-attribute matching from `0.1.1-dev.79`/`0.1.1-dev.80`.
